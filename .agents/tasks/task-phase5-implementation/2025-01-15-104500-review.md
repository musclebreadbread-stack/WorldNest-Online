# Chat hardening, fishing mini-game, and museum collection system

Three horizontal systems layered onto the existing ECS/inventory/quest architecture. Chat hardening (FEAT-001) moves message enforcement server-side via a Postgres RPC function that rate-limits, filters blocked words, and truncates. The fishing mini-game (FEAT-002) adds a timing-based state machine, biome-specific catch tables, and four new items. The collection/museum system (FEAT-003) introduces item donation tracking, category completion rewards, a new NPC Curator Milo, and a fourth quest objective kind (`donate`). All three follow the established pure-ops-over-components pattern and are testable without network access.

Watch for: the word filter uses plain substring matching which can produce false positives on compound words (confirmed); the `CollectionSystem` does not call `recordDonation` on the quest log so the `donate_first` quest cannot progress through the system path (confirmed); the fishing system rolls the catch at cast-time rather than reel-time, leaking the outcome before the player acts (confirmed, low severity for a single-player context).

**Verdict**: NEEDS_CHANGES

## High-level view

The chat RPC (`worldnest_send_chat`) is the single entry point for chat messages, enforcing rate limits by counting recent rows, filtering via a `blocked_words` table, and truncating to a configurable max length. The substrate limitation is the substring filter strategy, which will asterisk "grass" for containing "ass" and "Scunthorpe" for containing a slur — no word-boundary anchors are used.

The fishing system is a five-state state machine (`idle -> waiting -> biting -> caught/missed`) driven by `FishingSystem.update`. It deducts energy on cast, randomises a bite timer, and awards biome-specific fish on a successful reel-in within a timing window. The catch is determined at cast-time and stored on the component, which means a memory-reading client knows what fish is coming before the reel-in and the inventory-space check at cast-time may not match the specific item awarded at reel-time.

The collection module mirrors the quest/shop pattern: pure functions in `collectionOps.ts` over a `CollectionState` interface, with `CollectionSystem` consuming a `requestedDonation` flag each frame. Category completion auto-claims coin rewards. However, the system never notifies the quest layer, so `donate_first` can only be progressed by external code calling `recordDonation` directly, which the current `CollectionSystem` does not do.

The `donate` quest objective kind stores progress on the quest entry directly (like `talk`) rather than polling (like `collect`), which means it depends on `recordDonation` being called at the moment of donation. This creates a coupling contract that is documented in `questOps.ts` but not enforced by the system wiring.

<details>
<summary>Issues (4)</summary>

1. **Substring word filter false positives** — `regexp_replace` with a bare word pattern will match inside compound words (e.g., "crap" inside "scrap"). Use word-boundary anchors (`\m` and `\M` in Postgres regex) or switch to whole-word matching.
2. **CollectionSystem does not call recordDonation** — The `donate_first` quest objective depends on `recordDonation(questLog, discoveredCount)` being called on each successful donation. `CollectionSystem.update` never does this, so the quest cannot progress through the normal system path. Either inject a quest-log reference or emit a callback.
3. **Catch determined at cast-time** — `fishing.catchItemId` is set when the player casts, not when they reel in. A memory inspector reveals the outcome before the timing challenge. Low severity in this game's trust model.
4. **Fish item may be silently dropped** — `canFish` checks whether *any* fish type has inventory space, but the pre-rolled catch might be the one type whose stack is full. `addItem`'s return value (remainder) is not checked in `FishingSystem`, so the item is silently lost.

## Word filter substring matching

The migration's filter loop runs:

```sql
v_sanitized := regexp_replace(
  v_sanitized, v_word, repeat('*', length(v_word)), 'gi'
);
```

No word-boundary constraint. The current blocked-words list includes `crap` (matches inside `scrap`), `shit` (matches inside unlikely but possible compound words), and `damn` (matches inside `goddamn`, which is arguably acceptable). For a youth game where false positives create confusion, adding `\m` and `\M` word boundaries (Postgres regex) would tighten this without losing coverage:

```sql
v_sanitized := regexp_replace(
  v_sanitized, '\m' || v_word || '\M', repeat('*', length(v_word)), 'gi'
);
```

Confirmed by reading the migration at the `regexp_replace` call.

## CollectionSystem quest integration gap

`CollectionSystem.update` processes donations and auto-claims category rewards, but never calls `recordDonation` from `questOps.ts`:

```typescript
// CollectionSystem.ts, line 37-47
if (donate(collection, inventory, itemId)) {
  for (const category of COLLECTION_CATEGORIES) {
    if (
      isCategoryComplete(collection, category.id) &&
      !collection.categoryRewardsClaimed.has(category.id)
    ) {
      claimCategoryReward(collection, wallet, category.id);
    }
  }
}
```

The `donate_first` quest's objective is `{ kind: "donate", count: 1 }`, and `objectiveProgress` for `donate` reads `entry.progress` directly (like `talk`), meaning `recordDonation(questLog, collection.discovered.size)` must be called at donation time. The test file tests `recordDonation` in isolation but never through the system path. A player donating via the system would see the collection update but the quest would stay at 0/1.

The fix: inject a `QuestLog` reference into `CollectionSystem` (add `"quest"` to required components) or use the same callback pattern `NpcSystem` uses for `recordTalk`.

## Fishing catch pre-determination and item loss

In `FishingSystem.handleInteraction`, when the player starts fishing:

```typescript
fishing.catchItemId = rollCatch(biome, this.rng());
```

This happens at cast-time. The item is stored on the component for the duration of the waiting/biting states, making the outcome knowable before the timing challenge resolves.

The secondary consequence is more impactful: `canFish` checks whether *any* fish type has inventory space, but the pre-rolled catch might be the one type whose stack is full. The system doesn't check `addItem`'s return value:

```typescript
if (result === "success" && fishing.catchItemId) {
  addItem(inventory, fishing.catchItemId, 1);  // remainder not checked
  fishing.state = "caught";
}
```

This edge case requires a contrived inventory state (e.g., 49 common fish filling the only available slot, pre-roll lands on common), but it's a confirmed code path that silently drops an item. The fix is either to check `hasSpaceFor(inventory, fishing.catchItemId, 1)` before awarding, or to roll the catch at reel-time when the space check can be precise.

## Missing index for rate-limit query

The rate limiter counts messages per player per minute on every send:

```sql
select count(*) into v_recent from public.chat_messages
where sender_id = v_player and created_at > now() - interval '1 minute';
```

Migration 006 does not create an index on `(sender_id, created_at)`. At launch scale this is fine, but at sustained load the per-send COUNT against a growing table will degrade. **Likely** performance concern. Fix: `CREATE INDEX IF NOT EXISTS idx_chat_messages_sender_recent ON chat_messages (sender_id, created_at DESC)`.

## Test gaps

Not tested: the integration path where `CollectionSystem.update` should trigger quest progress. Not tested: `addItem` overflow in `FishingSystem` when the pre-rolled catch type has no space. Not tested: word filter behavior with compound words (tested with "hello damn world" but not with a word containing a blocked substring like "scrapyard").
