# Achievement system, cooking mini-game, and seasonal festivals

Phase 6 adds three horizontal-progression features to WorldNest Online: an 8-badge achievement system that polls entity state each frame, a 4-recipe cooking mini-game with an NPC (Chef Bao) and food energy restoration, and a 4-festival seasonal event system tied to the world clock. All three follow the established ECS pattern (pure-data component, definitions file, ops file, system) and maintain i18n parity across 12 locales.

Watch for: the `big_spender` achievement uses `wallet.coins` (current balance) as a proxy for "total coins earned" — spending coins lowers the counter, making the achievement harder to trigger than intended (confirmed). The `full_gathering` achievement definition uses `{ kind: "donate", count: 5 }` as its condition but relies on a hard-coded special case in `checkAchievement` rather than expressing its real requirement in the condition type (confirmed). The CookingSystem's terminal-state-reset-in-same-frame pattern means the HUD can never observe `done` or `failed` states (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The achievement system polls counters from existing components every frame and unlocks badges when thresholds are met. It deliberately unlocks only one achievement per frame to avoid double-payouts. The `big_spender` achievement compares against `wallet.coins` — a balance that decreases when the player buys things — so it really measures "current wealth" not "lifetime earnings," diverging from the description ("earn 200 coins through your adventures").

The cooking system replicates the fishing system's state-machine-plus-request pattern: the HUD sets a request field, the system consumes it next frame. The terminal states (`done`/`failed`) are immediately reset to `idle` within the same update call, so they exist for at most zero frames of observable time. If the HUD reads state on its own tick, it will never see a completion message.

The festival system introduces a day-based activation mechanism and per-cycle reward claiming. The cycle-key approach (`festivalId:cycleNumber`) prevents double-claims across seasons without requiring a seasonal reset.

## `big_spender` measures current balance, not lifetime income

In `AchievementSystem.buildSource`:

```typescript
totalCoinsEarned: wallet.coins,
```

`wallet.coins` is the player's current balance — it goes down when they buy items from the shop (`wallet.coins -= cost` in `shopOps.ts`). The `big_spender` achievement's description says "earn 200 coins through your adventures," implying a monotonically-increasing counter. A player who earns 300 coins but spends 150 will have 150 in their wallet and never trigger the achievement until they earn another 50, contradicting the promise.

The fix: add a `totalCoinsEarned` counter to `AchievementComponent` (or `WalletComponent`) that is incremented whenever coins are added (quest rewards, sell revenue, festival rewards, achievement payouts) but never decremented on purchases. The system should read that field instead of `wallet.coins`. (confirmed)

## `full_gathering` relies on a hard-coded ID check

The `full_gathering` definition declares its condition as `{ kind: "donate", count: 5 }`:

```typescript
{
  id: "full_gathering",
  condition: { kind: "donate", count: 5 },
}
```

But `checkAchievement` special-cases it:

```typescript
if (definition.id === "full_gathering" && !source.gatheringCategoryComplete) {
  return false;
}
```

The condition type system is lying — the `donate` condition alone would be satisfied by any 5 donations, but the real requirement is "gathering category complete AND 5 donations." If someone adds another achievement with a category-complete condition, they'd have to add another ID check. A dedicated condition kind (`{ kind: "category_complete", categoryId: "gathering" }`) would let the generic switch handle it. (confirmed)

## Cooking terminal-state-reset timing

In `CookingSystem.update`, after completing a cook or failing:

```typescript
// Reset terminal states back to idle after one frame
if (cooking.state === "done" || cooking.state === "failed") {
  cooking.state = "idle";
  cooking.selectedRecipe = null;
  cooking.timer = 0;
  cooking.version++;
}
```

This check runs unconditionally at the end of the same `update()` call that transitions to `done` or `failed`. The `version` bump happens twice in the same frame (once on completion, once on reset), which the HUD might use to detect "something happened," but it cannot distinguish success from failure by observing state. If the UI's render cycle happens between system ticks, it will always see `idle`.

The other state machines in this codebase (fishing) expose terminal states for at least one frame before resetting. To match that pattern: defer the reset to the next `update()` call by tracking whether the terminal state was just entered this frame. (confirmed)

## Unreachable `selecting` state

`CookingState` includes five states — `idle`, `selecting`, `cooking`, `done`, `failed` — but no transition in `cookingOps.ts` or `CookingSystem.ts` ever enters `selecting`. The implementation skips directly from `idle` to `cooking` (the recipe ID is carried in `requestedCook`). Either remove the dead variant or implement the selection flow if the HUD will need it. (confirmed)

## Achievement ordering bias

`AchievementSystem` breaks out of the definition loop after the first unlock:

```typescript
for (const definition of ACHIEVEMENT_DEFINITIONS) {
  if (checkAchievement(achievement, definition, source)) {
    unlockAchievement(achievement, definition.id);
    break;
  }
}
```

Achievements defined earlier in the array will always unlock before later ones when multiple conditions become true simultaneously. This creates an implicit coupling between definition order and player experience — future definition authors should be aware that position in the array determines unlock priority. (confirmed — informational, no fix needed)

## Test coverage gaps

Not tested:

- `fruit_salad` energy restoration (the other three foods are tested directly, but `fruit_salad` consumption is never asserted).
- The scenario where `completeCooking` is called after ingredients were consumed by another system between start and completion (the defensive re-check exists in code but tests always have ingredients available).
- The `big_spender` achievement through `AchievementSystem.update` (only tested at the `checkCondition` unit level).
