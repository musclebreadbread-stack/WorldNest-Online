# Achievement system, cooking mini-game, and seasonal festivals (v2)

Phase 6 adds three horizontal-progression features: an 8-badge achievement system with polled conditions, a 4-recipe cooking mini-game with Chef Bao NPC and food energy, and a 4-festival seasonal event system tied to the world clock. The fix commit (5198720) addressed all four v1 issues: `big_spender` now uses a `totalCoinsEarned` accumulator on `AchievementComponent`, `full_gathering` uses a generic `category_complete` condition kind, cooking terminal states persist for one frame before reset, and the unreachable `selecting` state was removed.

Watch for: the `totalCoinsEarned` accumulator is only incremented by achievement reward payouts, not by selling items, quest rewards, collection rewards, or festival rewards — so `big_spender` still cannot fire from normal gameplay (confirmed). The `totalFishCaught` and `totalQuestsCompleted` fields are never written by any production system, making `first_fish`, `fish_master`, and `quest_master` achievements permanently locked (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

All four v1 fixes land correctly. The cooking terminal-state reset uses `continue` at the top of the next iteration, matching the fishing system's pattern. The `category_complete` condition kind generalizes the full_gathering check. The dead `selecting` variant is gone.

The remaining gap is wiring: `AchievementComponent` declares three lifetime counters (`totalCoinsEarned`, `totalFishCaught`, `totalQuestsCompleted`) but no production system ever increments them. Only `AchievementSystem` itself writes `totalCoinsEarned += def.rewardCoins` when paying achievement rewards. The `FishingSystem`, `QuestSystem`, `ShopSystem` (sell), `FestivalSystem` (reward), and `CollectionSystem` (reward) all add coins to `wallet.coins` without touching the accumulator. Tests set these fields directly to verify the polling logic, but at runtime the values stay at zero. Five of eight achievements (`big_spender`, `first_fish`, `fish_master`, `quest_master`, plus `builder_10` which depends on the injected counter defaulting to `() => 0`) cannot trigger without external integration.

<summary>Issues (2)</summary>

1. **`totalCoinsEarned` only accumulates achievement rewards** — The only production write is `achievement.totalCoinsEarned += def.rewardCoins` in `AchievementSystem`. Selling items (`shopOps`), quest rewards (`questOps`), collection rewards (`collectionOps`), and festival rewards (`festivalOps`) all add to `wallet.coins` without touching this accumulator. The `big_spender` threshold (200 coins) is unreachable through normal play since other achievement rewards sum to at most 220 — requiring nearly all other achievements first. Add `achievement.totalCoinsEarned +=` at each income site, or introduce a single `earnCoins` helper that bumps both `wallet.coins` and the accumulator.
2. **`totalFishCaught` and `totalQuestsCompleted` are never incremented in production** — `FishingSystem` transitions to `caught` state and adds items to inventory but never writes to `AchievementComponent.totalFishCaught`. Similarly, `QuestSystem` marks quests completed without touching `totalQuestsCompleted`. The `first_fish`, `fish_master`, and `quest_master` achievements cannot trigger at runtime. Each system needs a cross-component write or an event that `AchievementSystem` can consume.

## Achievement accumulator wiring gap

`AchievementSystem.buildSource` reads from the component's own accumulators:

```typescript
fishCaughtCount: achievement.totalFishCaught,
totalCoinsEarned: achievement.totalCoinsEarned,
questCompletionCount: achievement.totalQuestsCompleted,
```

The four coin income sites that bypass the accumulator:

```typescript
// shopOps.ts – selling items
wallet.coins += payout;

// questOps.ts – quest completion reward
wallet.coins += definition.rewards.coins;

// collectionOps.ts – category completion
wallet.coins += category.rewardCoins;

// festivalOps.ts – festival reward
wallet.coins += rewardCoins;
```

The only production write to `totalCoinsEarned` is in `AchievementSystem` itself when paying out achievement rewards. A player who sells 300 coins worth of crops, completes quests, and participates in festivals will still have `totalCoinsEarned === 0` (or only the sum of previously-unlocked achievement rewards). The `big_spender` condition (`totalCoinsEarned >= 200`) becomes a late-game curiosity rather than a mid-game milestone.

`FishingSystem` detects a catch and adds the fish to inventory but does not require `AchievementComponent` in its component list and never increments `totalFishCaught`. The same applies to `totalQuestsCompleted`: `questOps.completeQuest` transitions quest state to `"completed"` without bumping the counter.

Fix options:

- Introduce lightweight helpers (`earnCoins`, `recordFishCaught`, `recordQuestCompleted`) called at each action site, keeping the coupling in shared utilities rather than cross-system component access.
- Have `AchievementSystem` derive counts from existing data where possible (e.g., `collection.discovered` for donations). This won't work for lifetime counters like fish caught, since fish can be sold or consumed after catching.

## Cooking terminal-state input latency

The `continue` after the terminal-state reset means a `requestedConsume` or `requestedCook` set on the same frame as a terminal state won't be processed until the frame after reset — one frame of input latency on the transition back to active use. The fishing system has the same `continue` pattern after resetting `caught`/`missed`, so this is consistent but worth documenting for HUD implementers who might wonder why a cook-request posted during the "done" frame takes two ticks to start.
