# WorldNest Online MVP foundation

This change implements a greenfield monorepo for a browser-based 2D MMO: ECS game engine, simplex-noise procedural world generation, Phaser 3 rendering, Supabase auth + realtime multiplayer, and a Next.js 14 frontend. The monorepo uses pnpm workspaces with turborepo orchestration, splitting concerns into `@worldnest/shared`, `@worldnest/game-engine`, `@worldnest/database`, `@worldnest/ui`, and `@worldnest/web`. The architecture separates pure-logic ECS from Phaser rendering and keeps database concerns in their own package, but several gaps will block scaling toward the MMO target.

Watch for: The ECS world update iterates all entities per system with O(N*S) entity filtering every frame (confirmed). The database TypeScript types diverge from the actual SQL schema (confirmed). Auth has no route protection—the game page is accessible without authentication (confirmed). Network sync builds payloads but nothing wires them to `RealtimeManager.broadcastPosition` (confirmed). Chunk rendering creates one Phaser Sprite per tile (256 sprites per chunk, 2304 for 9 chunks), which will collapse performance once real art assets are loaded (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The ECS framework has no indexing or archetype structure—`World.update()` filters all entities per system per frame. Performance will degrade as remote players accumulate. For single-digit entity counts this won't be noticeable, but it sets an early ceiling on the MMO path.

World generation is well-structured: deterministic seeded simplex noise with elevation/moisture/detail octaves, a WorldManager that streams a 3x3 chunk grid with proper load/unload callbacks, and solid test coverage proving determinism and boundary conditions.

Auth and realtime multiplayer are structurally present but not connected end-to-end. The `RealtimeManager` exposes `broadcastPosition` and presence tracking, but `NetworkSyncSystem` produces `pendingPayloads` that nothing consumes. Remote player sprite methods (`addRemotePlayer`/`removeRemotePlayer`) are never called. The `AuthProvider` component is never mounted in the component tree, so session restoration on refresh is broken.

The database migration defines `profiles`, `player_state`, and `worlds` tables, but `types.ts` references a non-existent `players` table with different columns. This will produce runtime failures the moment anyone writes typed queries.

Every tile in every loaded chunk creates a separate `Phaser.GameObjects.Sprite`—2,304 sprites for 9 chunks. A `TilemapLayer` or `RenderTexture` per chunk is needed before real art assets are introduced.

## ECS performance ceiling

The `World.update()` method converts the entities Map to an array, then for each of the 5 systems calls `.filter()` against every entity:

```typescript
update(deltaTime: number): void {
  for (const system of this.systems) {
    const matchingEntities = this.getEntities().filter((entity) => system.matches(entity));
    system.update(matchingEntities, deltaTime);
  }
}
```

With 5 systems and 100 remote players, that's 500 `matches()` calls per frame, each checking 2-3 `hasComponent` lookups. At 60fps, 30,000 map lookups per second for matching alone. For the MMO target this needs archetype indexing (entities grouped by component signature) or at minimum a cached query that invalidates on component add/remove.

## Network sync dead end

`NetworkSyncSystem` accumulates `pendingPayloads` and exposes `getPendingPayloads()`, but the GameScene never calls this method. The intended flow:

```
InputSystem -> MovementSystem -> NetworkSyncSystem (marks dirty, builds payload)
                                         |
                              GameScene calls getPendingPayloads()
                                         |
                              RealtimeManager.broadcastPosition()
```

The last two steps don't exist. The `RealtimeManager` in `@worldnest/database` is never instantiated in the web app. The GameScene has `addRemotePlayer`/`updateRemotePlayer`/`removeRemotePlayer` methods but no code invokes them. Multiplayer is structurally scaffolded but inert.

## Supabase client instantiation pattern

Every function in `auth.ts` calls `createSupabaseClient()` which calls `createClient()` fresh:

```typescript
export async function signIn(email: string, password: string) {
  const client = createSupabaseClient(); // new instance every call
  const { data, error } = await client.auth.signInWithPassword({...});
}
```

Supabase JS stores session tokens in a `StorageAdapter`. In browser environments the default is `localStorage`, so multiple client instances happen to share state. But in SSR or edge contexts (Next.js middleware, server components), there is no persistent storage, and a fresh client has no session. This also means the `onAuthStateChange` listener in one client instance won't fire for auth events triggered by a different instance. A singleton (or at minimum a module-level cached client) would make the session lifecycle explicit.

## Database type/schema divergence

The SQL migration creates:
- `profiles` (id, username, avatar, created_at)
- `player_state` (player_id, x, y, chunk, last_online, inventory)
- `worlds` (id, name, seed, created_at)

The TypeScript `Database` interface defines:
- `players` (id, name, avatar, level, position_x, position_y, created_at, updated_at)
- `worlds` (id, seed, name, created_at)

The `players` table doesn't exist. `profiles` and `player_state` aren't represented in the types. Any typed query will either fail at runtime or silently return wrong shapes.

## AuthProvider never mounted

The app layout (`layout.tsx`) renders `<Providers>` which contains only `QueryClientProvider`. The `AuthProvider` component exists but is never imported or rendered. The `onAuthStateChange` listener is never established, so returning users with valid Supabase sessions won't have auth state restored on page refresh. The auth page works by directly calling `signIn` and setting store state manually, but that state is lost on navigation or refresh.

## Tile rendering scalability

Each chunk is 16x16 = 256 tiles. With a 3x3 load radius, 9 chunks = 2,304 individual `Phaser.GameObjects.Sprite` instances. Each sprite occupies a game object slot with transform, bounds, and event processing overhead. The placeholder textures (6 solid-color 16x16 rects) batch well, but once real art assets with sprite variations are introduced, draw call count will spike.

The standard Phaser approach for tile grids is `Tilemap` + `TilemapLayer`, which uses a single draw call per layer regardless of tile count. Alternatively, a `RenderTexture` per chunk (render tiles once, re-render only on content change) would keep the active object count at 9.

## Unguarded game route

The game page at `/game` renders unconditionally. There's no middleware, no redirect, and no conditional rendering based on auth state. Either Next.js middleware checking for a Supabase session cookie, or a client-side guard in `GamePage` that redirects to `/auth` when `useAuthStore` reports no user, is needed.
