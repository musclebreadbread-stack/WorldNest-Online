# WorldNest Online MVP — v2 review

All seven issues from the v1 review have been addressed. ECS query caching replaces per-frame filtering, network sync payloads flow to RealtimeManager, database types match the SQL migration, the game route has an auth guard, tile rendering uses RenderTexture, the Supabase client is a singleton, and AuthProvider is mounted in the component tree. The fixes are structurally sound and introduce no regressions at the architectural level.

Watch for: The `RealtimeManager` is never instantiated or connected to the scene in the running app—`setRealtimeManager` is exposed but nothing calls it, so multiplayer remains inert (confirmed). Query cache does not auto-invalidate when components are added/removed on entities already in the World—the API silently serves stale results if the contract is violated (confirmed). The auth guard is client-side only; the `/game` route's JS bundle is still served to unauthenticated users before the redirect fires (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The network sync pipeline is now structurally complete inside the scene: `NetworkSyncSystem` produces payloads, `flushNetworkPayloads()` drains them to `RealtimeManager.broadcastPosition()`, and `setRealtimeManager` wires remote-player callbacks. The missing link is that nobody instantiates a `RealtimeManager` and passes it to the scene. The `realtimeManager` field stays null for the lifetime of the scene, and the `if (!this.realtimeManager) return` guard silently discards every payload. Multiplayer is wired in-process but never connected to a Supabase channel.

The ECS query cache solves the O(N×S) filtering problem for the steady state. The invalidation gap—`Entity.addComponent()` and `removeComponent()` don't notify the World—is documented by the test suite and is safe given that current code never mutates an entity's component set after registration. The risk is that both methods are public and unrestricted; nothing prevents future code from adding a component to a live entity and silently getting wrong query results.

The client-side auth guard prevents rendering and redirects to `/auth`, but operates entirely post-hydration. The server still ships the full page bundle to any requester. For an MVP where game logic isn't secret this is low-risk, but a Next.js middleware would close the gap.

1. **RealtimeManager never instantiated in the web app** — `GameScene.setRealtimeManager()` exists but nothing in the app creates a `RealtimeManager` instance, calls `joinRoom()`, or passes it to the scene. Add a `useEffect` in `GameCanvas` (or a scene lifecycle hook) that creates the manager after auth and calls `setRealtimeManager`. (confirmed)
2. **Query cache stale on component add/remove** — `Entity.addComponent()` and `removeComponent()` don't notify the World, so the cache can serve stale results if components are added to an entity that's already registered. Consider having `Entity` accept a `World` reference to invalidate automatically, or documenting this as a hard contract that entity archetypes are frozen after `addEntity`. (confirmed)
3. **Auth guard is client-only** — The `/game` route has no server-side middleware. The page bundle is served to unauthenticated requests before the client-side redirect triggers. A Next.js middleware checking the Supabase session cookie would prevent even the bundle delivery. (confirmed)

## RealtimeManager integration gap

The fix adds `flushNetworkPayloads()` in the game loop and a `setRealtimeManager()` setter on the scene:

```typescript
private flushNetworkPayloads(): void {
  if (!this.realtimeManager) return;
  const payloads = this.networkSync.getPendingPayloads();
  for (const payload of payloads) {
    // ...
    this.realtimeManager.broadcastPosition(broadcastPosition);
  }
}
```

Since nothing in the web app creates a `RealtimeManager` or calls `setRealtimeManager`, the guard returns immediately every frame and payloads accumulate in `NetworkSyncSystem` until `getPendingPayloads()` drains them into the void. The intended integration path—instantiate `new RealtimeManager(user.id, user.username)`, call `joinRoom("default")`, then `gameScene.setRealtimeManager(manager)`—doesn't exist anywhere in the codebase. The `GameCanvas` component mounts Phaser and destroys it on unmount but never touches realtime.

## Query cache invalidation boundary

`Entity.addComponent()` and `removeComponent()` are public, unrestricted methods that don't hold a reference to the World. The cache invalidation is triggered only by `World.addEntity()` and `World.removeEntity()`. The test suite explicitly documents the manual `invalidateQueryCache()` escape hatch, but no JSDoc or type-level constraint communicates the "frozen archetype" contract to consumers of the API. A future contributor adding a component to a live entity will get silently wrong query results with no error.
